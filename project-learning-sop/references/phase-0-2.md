# Phase 0-2 详细指引：目标设定、项目概览、目录结构

> 本文件在 Phase 0 开始时与 `references/workflow-state.md` 一起读取，覆盖 Phase 0、1、2 的项目分析细节；模式、状态结构和恢复规则以 workflow-state 为准。

## Phase 0：目标设定与前置检查

### 0.1 确认项目来源

开场先与学习者确认项目来源，三选一：

- **本地目录**：询问项目绝对路径（如 "学习 D:\code\my-project"）。
- **GitHub 链接**：先确认克隆目标位置，再执行 `git clone <url> <目标目录>`。默认保留完整历史；只有确认本次不需要历史分析时才用 `--depth 1`，并在 Phase 6 前执行 `git fetch --unshallow` 补全历史。
- **当前工作目录**：直接使用当前目录。

如果学习者什么都没提供（第一次触发本技能），先用一段欢迎语说明能力，再询问：

> 我可以带你从 0 到 1 系统学习任何一个项目：先看懂它解决什么问题、怎么跑起来，再沿着真实功能链路读代码，最后动手改一个小功能验证理解。整个过程我会一步一步引导你，并帮你生成"项目地图"笔记。
> 请告诉我：你想学习哪个项目？（本地路径 / GitHub 链接 / 就在当前目录）

### 0.2 确认学习目标层级（缩小搜索空间）

使用当前环境可用的用户输入机制，或直接用一个简短问题让学习者选择目标层级。选项按从宽到窄排列：

1. **整体理解**——知道项目解决什么问题、核心模块、主要流程（适合第一次接触）
2. **理解一个子系统**——如"Kubernetes Scheduler 怎么选 Node"（适合有一定基础）
3. **理解一个功能**——如"登录功能完整链路"
4. **理解一次调用**——如"一个 Tensor 操作如何执行"（最窄、最深入）

**指导原则**：目标越窄，学得越深。建议新手从“整体理解 + 一个功能”起步。把最终目标记录进 `notes/working.md`，后续所有 Phase 都围绕该目标服务，不要蔓延。

### 0.3 确认 Git 基础

用 1-2 个问题确认学习者是否会用以下命令（不会的现场用 2 分钟教）：

| 命令 | 学习场景中的用途 |
| --- | --- |
| `git clone` | 下载仓库 |
| `git status` / `git diff` | 查看改动（Phase 8 修改实践必用） |
| `git log` | 看提交历史（理解代码演进） |
| `git blame` | 定位某行代码是谁在哪个 commit 改的（理解"奇怪代码"） |
| `git branch` / `git switch` | 查看和切换分支 |

若学习者完全没接触过 Git，先用 5-10 分钟做一个微型练习（在任意临时目录 clone 一个小仓库并改一行代码），再进入正式学习。

### 0.4 确定权限与建立内部工作底稿

先逐项记录是否获准：运行项目命令、安装依赖、写学习文件、修改源码、创建分支、提交代码。未明确授权的项目按只读方式学习。

默认在目标仓库之外创建独立学习工作区，并在其中创建 `notes/`。只有学习者明确同意时才把 `notes/` 放进目标仓库。所有写入前记录目标绝对路径，避免污染现有工作树。

按 `references/workflow-state.md` 的唯一状态模板初始化 `notes/working.md`。本文件后续的所有 Phase 产出都追加到该状态文件的“学习内容”和“证据账本”，不要另建文件。

## Phase 1：项目概览

### 1.1 资料阅读顺序（从高价值到低价值）

1. `README.md`——速览：项目是什么、技术选型、功能清单、快速启动、架构图、注意事项。
2. `CONTRIBUTING.md`——了解开发流程与规范（也为 Phase 8 改代码做准备）。
3. `docs/` 目录——官方文档；成熟项目常含"快速开始"和"架构设计"章节。
4. GitHub Wiki（如存在）——重点看"快速启动"与"项目结构介绍"。
5. Release 页面——了解版本演进（可选）。
6. Issues——速览已知问题与项目活跃度（不细读，Phase 6 再深入）。

**注意**：不要通篇阅读文档。AI 先通读并提炼要点，把最核心的 3-5 条讲给学习者。

### 1.2 五个基本问题（AI 分析后引导学习者回答）

AI 完成资料阅读后，用提问引导学习者逐题回答（学习者答不上来时给出提示，不是直接给答案）：

1. **这个项目解决什么问题？**（一句话说清痛点）
2. **谁会使用它？**（目标用户画像）
3. **最核心的功能是什么？**（3 个以内）
4. **它属于哪一类？**（CLI / Web 应用 / 数据库 / 中间件 / 框架 / SDK / 基础设施）
5. **如何启动它？**（README 里的快速开始命令）

**判断技巧（仅作 E0 假设，必须再用配置、源码或运行证据验证）**：
- 有 `package.json` 且有 `start` 脚本 → Web 应用/CLI
- 有 `pyproject.toml` + `__main__.py` → Python CLI/库
- 有 `Cargo.toml`/`go.mod` → Rust/Go 项目
- 有 `Dockerfile`/`docker-compose.yml` → 常以容器运行的基础设施/服务
- 有 `k8s/`、`operator/` 目录 → 云原生基础设施

### 1.3 验证理解

让学习者**用自己的话**写一句“这个项目是什么”（不超过 50 字），追加到 `notes/working.md`。判断标准：能说清“给谁用的、解决什么问题”，而不是复读 README 标题。

### 1.4 产出：追加到 `notes/working.md`

```markdown
## 项目概览
- **一句话描述**：<学习者的原话>
- **解决什么问题**：<痛点>
- **目标用户**：<画像>
- **核心功能**：<1-3 项>
- **项目类型**：<CLI / Web / DB / 中间件 / 框架 / SDK / 基础设施>
- **技术栈速览**：<语言、主要框架、数据存储>
- **启动方式**：<README 中的快速开始>
```

## Phase 2：目录结构与技术栈地图

### 2.1 目录职责解读（上帝视角）

AI 先列出顶层目录，与学习者一起完成下面的职责对照（常见模式）：

```text
project/
├── src/          # 核心实现（也可能是 lib/、app/、core/）
├── tests/        # 测试（也可能 test/、__tests__/、spec/）
├── docs/         # 文档
├── examples/     # 使用示例（教你怎么用的最佳材料）
├── scripts/      # 开发/构建/发布工具脚本
├── config/       # 配置文件（也可能 .config/、settings/）
├── migrations/   # 数据库迁移脚本
└── README.md
```

**不需要理解每个目录内部**，目标是回答："这个仓库大概是怎么组织的？"

### 2.2 关键配置文件速查表

| 文件 | 项目类型 | 能看出什么 |
| --- | --- | --- |
| `package.json` | Node.js | 依赖、scripts、入口、构建工具 |
| `pom.xml` | Java (Maven) | 依赖、插件、模块划分 |
| `build.gradle` / `build.gradle.kts` | Java (Gradle) | 依赖、多模块、构建逻辑 |
| `requirements.txt` / `pyproject.toml` | Python | 依赖、构建工具（setuptools/poetry/uv） |
| `Cargo.toml` | Rust | 依赖、workspace 成员 |
| `go.mod` | Go | 依赖、Go 版本、模块名 |
| `Dockerfile` / `docker-compose.yml` | 任意 | 部署方式、服务组成 |
| `Makefile` / `justfile` / `Taskfile.yml` | 任意 | 常用开发命令入口 |

### 2.3 从依赖推断架构模式（经验积累）

- 看到 AOP / Aspect 依赖 → 项目用了切面编程（常见于日志、权限横切逻辑）
- 看到 freemarker / thymeleaf → 服务端模板渲染，资源目录有模板文件
- 看到 Redisson / Lettuce → 有 Redis 客户端初始化与缓存/分布式锁逻辑
- 看到 SQLAlchemy / Prisma / TypeORM → 有 ORM 层，实体类与表对应
- 看到 gRPC / Protobuf → 微服务间通信，有 .proto 文件
- 看到 WebSocket 库 → 有长连接实时功能

### 2.4 验证理解

问学习者 2-3 个问题，例如：

- "这个项目分哪几个大模块？哪个目录是核心实现？"
- "从依赖来看，它用了什么数据库/缓存/消息队列？"
- "构建和测试命令是什么？"

答对即可进入 Phase 3。

### 2.5 产出：追加到 `notes/working.md`

```markdown
## 目录结构与技术栈

### 目录职责表
| 目录 | 职责 |
| --- | --- |
| src/ | <核心实现> |
| tests/ | <测试> |
| ... | ... |

### 技术栈
- 语言/运行时：<...>
- 框架：<...>
- 存储：<...>
- 其他关键依赖：<...>

### 扩展机制（重要）
- <基类/继承？插件？注册表？——"如何加新东西"是 guide.md 第 8 节的素材>

### 常用命令
- 安装依赖：<...>
- 启动：<...>
- 测试：<...>
- 构建：<...>
```

### 2.6 跳过规则

- 项目极简单（单文件脚本、<200 行）时，Phase 1-2 可合并快速完成，但"一句话描述 + 目录职责"仍要写入 working.md。
