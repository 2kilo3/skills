# Phase 3-4 详细指引：运行项目、行为流程与数据模型

> 本文件在 Phase 3 开始时读取，覆盖 Phase 3（运行项目）与 Phase 4（业务与数据）的完整操作细节。

## Phase 3：运行项目（最重要的一步）

### 3.1 标准启动流程

```bash
git clone <repo-url>   # 若尚未克隆
cd <repo>
# 记录 git status、commit SHA 与测试基线
# 安装依赖（按 README / Phase 2 笔记中的命令）
# 修改本地配置（数据库账号密码、端口等）
# 启动项目
# 运行测试（确保基线是绿的）
```

执行安装、配置或启动命令前，先说明命令用途、写入位置、网络访问和外部服务影响，并确认相应权限。若基线已有失败，记录失败数与错误摘要，后续验收以“不新增失败”为准。

### 3.2 运行排错四要点（逐个排查）

1. **环境版本一致性**：Node.js / JDK / Python 等运行时版本需匹配项目要求（看 `.nvmrc`、`engines` 字段、`.tool-versions`、README 要求）。
2. **依赖版本一致性**：数据库（MySQL/PostgreSQL/Redis 等）版本别用太新或太旧；中间件如 RocketMQ、Kafka 注意项目要求的版本。
3. **本地配置覆盖**：数据库账号密码、API key、端口等改成学习者的；注意**确认读的是哪个配置文件**（dev/prod 环境变量优先级、`.env.example` → `.env`）。
4. **报错顺藤摸瓜**：读关键报错栈（第一行 + 最后一行），定位到具体文件去改；查不到就搜索引擎 + AI，但要把报错原文记录下来。

### 3.3 安全地缩小运行面

项目缺少 MinIO、RocketMQ、Redis 等外部服务时，按以下顺序降级：

1. 优先使用项目已有的 profile、feature flag、mock、example 或单元测试，不改源码。
2. 只运行与学习目标相关的最小命令或测试，避免为了一个链路启动全部服务。
3. 需要容器、服务安装或联网下载时，先说明资源和系统影响并取得授权。
4. 只有学习者明确授权源码修改后，才可以在独立分支做临时适配；记录 diff，并在验收前恢复或正式纳入任务。
5. 无法安全运行时切换为“静态证据模式”：依靠文档、配置、测试和调用链完成分析，并明确哪些运行结论尚未验证。

**运行预算**：快速导览默认不运行。深度带读只做与选定链路有关的一次最小成功运行和一次验证；获得所需 E3 证据后立即停止，不扩展到目标项目的其他交付、渲染或全量流程。完整实战才执行与修改验收有关的额外运行。

### 3.4 实际使用项目（建立"代码↔行为"对应）

运行成功后，必须让学习者**亲手使用**：

| 项目类型 | 使用方式 |
| --- | --- |
| CLI | 执行 `--help` 和 1-2 个真实命令，观察输出 |
| Web 应用 | 打开页面，完成 1 个核心操作（注册/登录/创建资源等） |
| 库/SDK | 运行官方 example 或写一个最小调用脚本 |
| 数据库/中间件 | 跑官方 demo 或执行一个最简单的读写操作 |
| 框架 | 运行脚手架生成的模板项目 |

**关键动作**：使用过程中引导学习者注意“我触发了什么 → 系统发生了什么”，这是 Phase 4 行为流程梳理和 Phase 6 调用链追踪的事实基础。

### 3.5 验证理解

- "项目跑起来了吗？你看到了什么？"（要求学习者描述运行成功的证据）
- "执行 `project run` 时，屏幕上哪个输出对应哪个代码文件？"（不需要精确，有感觉即可）

### 3.6 产出：追加到 `notes/working.md`

```markdown
# 运行记录

- **启动步骤**：<逐步命令>
- **运行成功证据**：<输出/页面截图描述/命令结果>
- **我实际使用了**：<做了什么操作、看到了什么>
- **遇到的坑与解法**：<报错信息 → 原因 → 解决方式>
- **注意事项**：<环境要求、配置项、临时禁用过什么（记得恢复）>
```

## Phase 4：行为流程与数据模型

### 4.1 梳理目标相关行为流程

原则：**从一次具体用户操作开始，而不是从模块图开始**。

方法（以聊天室系统为例）：

> 用户登录 → 用户上线 → 添加好友 → 创建房间 → 加入房间 → 发送消息 → 消息审核 → 其他用户接收 → 回复消息

操作步骤：
1. AI 根据代码与文档梳理 1-3 条与目标相关的流程（按优先级）。Web 用“用户动作 → 结果”，CLI 用“命令 → 解析 → 执行 → 输出”，库用“API 调用 → 核心逻辑 → 返回”，数据/ML 项目用“输入 → 变换/训练 → 输出”，基础设施用“事件 → 控制循环 → 状态变化”。
2. 与学习者确认哪条流程是他们最关心的（作为 Phase 6 的深读候选）。
3. 引导学习者把流程复述一遍（用自己的话，不用术语也行）。

**流程记录格式**（写入 `notes/working.md`，按项目类型替换“用户”措辞）：

```text
流程名：用户登录
用户输入邮箱密码
  → 前端校验格式
  → 发送 POST /login
  → 后端校验密码
  → 生成会话 Token
  → 返回用户信息
  → 前端保存状态并跳转
```

### 4.2 理解数据模型

| 项目类型 | 数据模型在哪里 | 怎么看 |
| --- | --- | --- |
| 数据库应用 | SQL 迁移文件 / ORM 实体类 | 本地初始化数据库后用可视化工具看 ER 图；或读迁移文件建表语句 |
| 内存/计算类 | 数据结构定义（struct/class/dataclass） | 直接读核心数据类型的字段定义 |
| 消息系统 | 消息 schema / proto / JSON 结构 | 读 schema 定义与生产者消费者代码 |
| 配置驱动 | 配置文件结构 | 读配置 schema 与默认值 |

**技巧**：比起直接读 SQL 文件，先在本地初始化数据库，再用可视化图表（DataGrip/DBeaver/命令行 `\d`）查看表关系，更直观。例如：房间表分单聊/群聊，一个房间含多个会话和消息——这种关系一眼可见。

### 4.3 验证理解

- 让学习者描述一条完整流程："用户点击 X 按钮之后，系统内部依次发生了什么？"
- 让学习者解释 2-3 张核心表/核心数据结构的关系。

### 4.4 产出：追加到 `notes/working.md`

```markdown
# 行为流程与数据模型

## 核心流程
<按 4.1 格式列出 1-3 条>

## 数据模型
- 核心实体：<实体名、关键字段、与其他实体的关系>
- 存储方式：<数据库/内存/文件/消息>

## 我的理解（学习者复述）
<学习者用自己的话写的流程说明>
```
