# Phase 8-9 详细指引：修改实践、验证与复盘

> 本文件在 Phase 8 开始时读取，覆盖 Phase 8（修改实践）与 Phase 9（验证复盘）的完整操作细节。

## Phase 8：修改实践（从 0 到能改代码）

进入本阶段前，必须已获得修改源码的明确授权。未授权时跳过实践并记录“未完成实践毕业”，不得把学习交付误报为完整毕业。

### 8.1 任务梯度（从易到难，至少完成 1 个实质任务）

| 级别 | 任务类型 | 示例 | 涉及理解 |
| --- | --- | --- | --- |
| L1 | 修改日志/错误信息 | 给某条日志加上项目前缀、改一个报错文案 | 日志在哪里输出 |
| L2 | 增加配置项 | 增加 `--verbose` 参数、新增一个可配置的阈值 | 参数/配置在哪里解析、如何传递 |
| L3 | 增加一个测试 | 给核心函数补一个用例 | 测试怎么写、被测函数行为 |
| L4 | 修复一个简单 bug | 从项目 Issues 里挑一个 easy bug | 完整调用链 + 根因分析 |
| L5 | 增加小功能/example | 新增一个命令、一个 example 文件 | 功能注册机制、模块间耦合 |

**选择原则**：
- L1-L2 是可选热身，不能单独满足毕业标准。
- 至少完成一项 L3-L5 或同等复杂度的实质任务，并与学习者目标匹配（目标为“整体理解”可做 L3；目标为“改功能”可做 L5）。
- 若项目 Issues 里有标着 `good first issue` 的 bug，优先选它做 L4。

### 8.2 每个任务的完整流程（引导式）

1. **学习者自行定位**：AI 提问"这个需求，你觉得应该改哪个文件？"，学习者先猜，AI 用 6.2 的调用链记录引导（"想想登录链路里哪层负责校验？"）。
2. **AI 确认修改点**：学习者定位后，AI 验证并指出精确文件与行。
3. **学习者动手改**（或口述修改方案由 AI 代写——但必须让学习者说明每一行改动的理由）。
4. **运行验证**：启动相关功能，观察行为变化。
5. **跑相关测试**：`pytest <file>` / `npm test -- <file>` 等定向测试；全量测试在 Phase 9 跑。
6. **记录**：追加到内部底稿 `notes/working.md`。

### 8.3 修改实践纪律

- **分支需授权**：获得创建分支的授权后再用 `git switch -c learn/xxx`；否则只在学习者指定的现有工作方式下操作。
- **提交需单独授权**：只有学习者明确要求提交时才创建 commit；提交时每个任务一个 commit，message 说明改动。
- **临时修改标注**：Phase 3 为了启动做的临时改动（禁用依赖等）必须恢复或用 `git stash` 隔离。
- **不替学习者决定改什么**：任务选择权在学习者（AI 给选项：改日志？加配置？修 bug？）。
- **宁慢勿快**：一个任务没跑通不进入下一个。

### 8.4 产出：修改记录并入两份交付物

按下面的结构把每个任务记录进工作底稿 `notes/working.md`（供 Phase 9 汇总）：

```markdown
## 修改实践记录
### 任务 1：<描述>
- 级别：L<1-5>
- 改了什么：<文件 + 改动摘要>
- 为什么改这里：<学习者自己的理解>
- 如何验证：<运行了什么、看到了什么>
- 测试结果：<通过/失败 + 输出摘要>
```

最终映射：Phase 9 把修改任务写入 `guide.md` 第 8 节（扩展指南）与 `course.html` 模块 6（动手改代码）。**不单独生成笔记文件。**

## Phase 9：验证与复盘

### 9.1 质量验证

1. **全量测试**：运行项目完整测试套件，与 Phase 3 记录的基线比较（记录总数、通过数、既有失败和新增失败）；验收要求新增失败为 0。
2. **git diff 审查**：`git diff` 从头看一遍，确认没有遗留的调试代码、临时禁用、硬编码密钥。
3. **恢复检查**：确认 Phase 3 的临时修改已恢复。

### 9.2 复盘对话（引导学习者总结）

逐题让学习者回答：

1. 这个项目解决什么问题？——对比 Phase 1 的回答，现在能说得更准确吗？
2. 程序从哪里启动？——入口文件/命令是什么？
3. 核心模块有哪些？——各负责什么？
4. 一次典型请求如何经过系统？——画出/说出完整链路
5. 最重要的几个抽象是什么？——它们之间什么关系？
6. 测试在哪里？——怎么运行？
7. 为什么某些设计这样实现？——举 1-2 个例子（含 git 历史/PR 依据）
8. 如果要修改某个功能，应该从哪里开始？——用项目地图指出起点

按 `references/checklist.md` 的 0-2 分量表评分；满足总分和关键题阈值后才能宣称毕业。

### 9.3 基于最终源码快照生成交付物

1. 记录修改后的 commit SHA；未提交时记录工作树快照时间和 `git diff` 摘要。
2. 按 `references/guide-spec.md` 生成最终 `notes/guide.md`，只写入已重新验证的文件、符号、行号和代码摘录。
3. 按 `references/html-course-spec.md` 生成最终 `notes/course.html`。内容映射如下：

| guide.md 章节 | course.html 模块 |
| --- | --- |
| 项目速览 + 功能地图 | 模块 1：这个项目是什么（+ 实际用一次） |
| 目录结构导航 | 模块 2：认识主角（核心组件/类） |
| 核心概念 + 架构/数据流图 | 模块 3：零件怎么说话 |
| 行为流程 | 模块 4：一次操作背后（数据流动画） |
| 核心代码路径 + 导航表 | 模块 5：真实代码之旅（代码↔白话对照） |
| 扩展指南 + 修改实践 | 模块 6：动手改代码 |

4. 更新“还没理解”清单：哪些已解决、哪些保留。
5. 预览两份文件，修正内容、图表和交互问题后再交付。

### 9.4 产出最终交付（完整实战严格两份）

1. `notes/guide.md`（导航指南，最终版）——呈现给学习者，现场做一次"导航练习"（随机功能 → 找到对应文件/函数）。
2. `notes/course.html`（交互式课程，最终版）——随最终理解更新。
3. 下一步建议（写在学习者确认后）：
   - 继续深入：选择第二条调用链或更深的子系统，可重新触发本技能（目标层级调窄一档）；
   - 参与贡献：从 `good first issue` 开始，熟悉 PR 流程。

### 9.5 收尾

向学习者展示整个学习旅程的成果（**guide.md + course.html 两份交付物** + 修改实践成果），总结其在过程中"从完全陌生到能改代码"的跨越，并给出后续可选路线。
